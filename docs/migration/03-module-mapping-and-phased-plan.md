# 03 — Module mapping and phased migration plan

Status: **proposal**. Nothing in this document is implemented. No C++ source file
exists in the repository at the time of writing.

---

## 1. Governing rules

These are constraints, not aspirations. A phase that violates one is not complete.

1. **The Rust node remains the reference and the release.** Until the final gate in
   §6, every published binary is the Rust one. The C++ tree is built by developers
   and CI, never shipped.
2. **No consensus change.** Chain ids, PoW, difficulty, subsidy, maturity,
   transaction format, sighash, script, genesis, and anchors are frozen exactly as
   audited in `01`. If the Rust code looks wrong, the C++ code reproduces the
   wrongness and the finding is recorded.
3. **No deletion.** No Rust file is removed, moved, or rewritten to make the port
   easier. The two implementations coexist.
4. **Byte equality where bytes are consensus, protocol acceptance where they are
   not.** Hashes, transactions, headers, and the state root must match byte for
   byte. JSON wire messages need only be accepted by the peer.
5. **Every phase ends with a gate that can fail.** A gate is a command with an exit
   code, not a judgement call.
6. **One source of truth for numbers.** No test count, block count, or hash is
   written into prose by hand (finding F11); it is generated by the harness.

## 2. Target repository layout `[PROPOSED]`

The Rust crate stays exactly where it is. The C++ implementation gets its own root
so that no build system has to understand the other language's tree.

```
zerocoin/                 # EXISTING Rust reference — untouched
cpp/
├── CMakeLists.txt        # top-level; options, targets, ctest hooks
├── cmake/
│   ├── Warnings.cmake
│   ├── Sanitizers.cmake
│   └── Secp256k1.cmake
├── include/zerocoin/     # installed public headers (kernel only)
├── src/
│   ├── kernel/           # consensus-only library
│   ├── policy/           # relay rules; may include kernel, never node
│   ├── node/             # p2p, rpc, wallet, storage, miner
│   │   ├── p2p/
│   │   ├── rpc/
│   │   ├── storage/
│   │   └── wallet/
│   ├── util/             # log, hex, datadir, base58, varint
│   ├── cli/              # zerocoin-cli
│   └── daemon/           # zerocoind
├── test/
│   ├── unit/             # C++ unit tests
│   └── bench/            # scratchpad and serialisation benchmarks
test/
├── functional/           # Python suite driving EITHER binary
│   └── test_framework/
└── vectors/              # captured golden vectors (JSON), committed
scripts/
├── build.sh
├── test.sh
├── capture_vectors.sh
└── parity.sh
docs/migration/
```

Why `cpp/` and not a new `src/`: the repository root already contains a Rust crate
named `zerocoin/` whose own `src/` is the reference. A second bare `src/` at the
root would be ambiguous in every path, log line, and review comment. `cpp/` also
makes the removal story trivial — the directory can be deleted without touching a
single reference path.

Why `test/functional` at the repository root rather than under `cpp/`: the harness
must be able to launch **both** binaries, so it cannot belong to either.

### 3.3 Explicitly out of scope for the first C++ milestone

| Rust | Decision |
|---|---|
| `gui.rs`, `ui/wallet.slint` | **Keep the Rust/Slint GUI.** It talks JSON-RPC; it can drive either daemon. Reimplementing a GUI in C++ is not required by the task and would multiply the work. `[PROPOSED]` |

## 4. Phases

Each phase lists **scope**, **deliverable**, and **exit gate**. The gate identifier
is used by `05-test-strategy.md` §7.

### P0 — Baseline capture (Rust only)

*Scope.* Build the Python harness and the vector-capture tooling. No C++ code.

*Deliverable.* `test/functional/test_framework/` (node lifecycle, CLI wrapper, port
allocator, datadir isolation); `scripts/capture_vectors.sh`; a committed corpus in
`test/vectors/` covering everything in `01` §14.

*Exit gate G0.*
- The corpus can be regenerated from the pinned Rust commit and is byte-identical
  across two runs on two machines.
- The Rust suite still reports 235 passing.
- Every vector file has a `source` field naming the exact command that produced it.

### P1 — Kernel primitives

*Scope.* Hash types, hex types, varint, serialisation framework, `uint256`,
transaction encoding.

*Deliverable.* `libzerocoin_kernel` with `hash`, `uint256`, `transaction`, `util`.

*Exit gate G1.*
- All hash, varint, and transaction serialisation vectors match.
- A `Hex256` / `Hex20` pair of types makes "storage order" and "display order"
  impossible to confuse at compile time (F3).
- `static_assert` on every width and constant.

### P2 — Ledger semantics

*Scope.* Script interpreter, sighash, signature verification via a vetted
secp256k1 library.

*Deliverable.* `kernel/script`, `kernel/sighash`, `kernel/keys`.

*Exit gate G2.*
- Every accept/reject vector in the script matrix matches, including the four
  limits and the single-`SIGHASH_ALL` rule.
- Sighash digests match for every vector.
- Signatures produced by Rust verify in C++ and vice versa; the DER encoding and
  low-S normalisation match.

### P3 — Consensus

*Scope.* Header, Merkle, difficulty, reward, PoW (trivial first, then scratchpad),
chain params, genesis, anchors.

*Deliverable.* The complete consensus library, with no I/O.

*Exit gate G3.*
- `GENESIS_COINBASE_TXID`, `GENESIS_MERKLE_ROOT`, `GENESIS_HASH_REGTEST`,
  `GENESIS_HASH_DEVNET`, `EMPTY_STATE_ROOT`, and `STATE_ROOT_LAYOUT_PROBE` all
  match.
- Header preimages and PoW hashes match for a fixed grid of headers on all three
  networks.
- The difficulty sequence matches for a synthetic 3,000-block history.
- The subsidy table matches at heights 0, 1, 209,999, 210,000, 13,440,000, and
  beyond the 64th halving.
- Scratchpad throughput is within the agreed factor of the Rust engine (§7).

### P4 — State machine

*Scope.* UTXO apply, `connect_block`, storage read, chain replay.

*Deliverable.* `kernel/validation`, `kernel/utxo`, `node/storage` (reader).

*Exit gate G4.*
- Replaying the captured 101-block regtest chain reproduces the tip hash,
  `state_root`, `subsidy_issued`, and UTXO count **at every height**.
- Every rejection vector is rejected with the same error class.
- An immature-coinbase block is rejected and the peer is isolated (F17).

### P5 — Node, RPC, wallet, wire

*Scope.* Persistence writer, P2P frame/handshake/message, RPC, wallet, keystore,
CLI.

*Deliverable.* A `zerocoind` binary that can join a Rust network.

*Exit gate G5.*
- C++ node completes a handshake with a Rust node and stays connected for an hour.
- Blocks and transactions propagate in both directions.
- The 12 RPC methods return the same fields and units for the same chain.
- A wallet file written by Rust opens in C++, and vice versa.
- The same seed phrase/key produces the same address and can spend the same coins.

### P6 — Differential soak

*Scope.* Both nodes on regtest and devnet under scripted and randomized load.

*Deliverable.* `scripts/parity.sh`, a soak report, and a divergence log.

*Exit gate G6.*
- 14 consecutive days of soak with zero divergence in tip hash, state root, and
  UTXO set.
- At least 100,000 regtest blocks and 10,000 transactions across the soak.
- Every divergence found is either fixed or recorded as a Rust defect and fixed in
  both implementations.

### P7 — Hardening and operations

*Scope.* Fuzzing, sanitizers, logging, benchmarks, CI, packaging.

*Deliverable.* Green CI on Linux/Windows/macOS × GCC/Clang/MSVC; fuzz corpus;
benchmark baseline.

*Exit gate G7.*
- 24 hours of frame/message fuzzing with no crash and no unbounded allocation.
- ASan/UBSan clean across the unit and functional suites.
- Logging categories implemented and used by the functional harness.
- A release build with LTO produces a binary that passes G5 and G6 again.

### P8 — Cutover decision

*Scope.* Decision, not code.

*Gate G8.*
- A written decision record signed off by the maintainers.
- Either: C++ becomes the release binary and Rust becomes the reference oracle; or:
  both ship and the Rust one remains default; or: the port is abandoned and the C++
  tree is archived without touching Rust.
- Whichever is chosen, **no Rust file is deleted in the same change.**

## 5. How a phase runs day to day

```
1. Capture or extend vectors from Rust (P0 tooling).
2. Write the C++ module against the vectors.
3. Run G-gate locally: scripts/build.sh && scripts/test.sh.
4. Run parity for the phase: scripts/parity.sh --phase Pn.
5. Commit only when the gate is green; the commit message names the gate.
```

Commits use conventional prefixes (`feat`, `fix`, `test`, `build`, `docs`,
`chore`) and reference the phase, e.g. `feat(kernel): add byte-exact transaction
serialisation (P1)`.

## 6. Dual-run strategy

Four complementary modes, in increasing cost and confidence.

| Mode | What runs | What it proves |
|---|---|---|
| **A. Replay** | Both implementations consume the same block file | Validity and state transition equality |
| **B. Live interop** | C++ node peers with a Rust node | Handshake, frames, JSON messages, sync |
| **C. Alternating mining** | Each node mines alternate blocks on one regtest chain | Each accepts the other's coinbase, timestamps, and difficulty |
| **D. Differential fuzz** | Random transactions and blocks submitted to both | Agreement on rejection *and* on the error class |

Mode D is the only one that finds disagreements in *invalid* data, which is where
consensus bugs hide. It requires both implementations to expose the same error
taxonomy; `01` §13 already names the classes (`ImmatureCoinbase`, `DoubleSpend`,
`NegativeFee`, …).

## 7. Performance expectations `[PROPOSED]`

The port exists partly because C++ is expected to be faster at the scratchpad PoW.
That expectation must be **measured**, not assumed.

- Baseline: Rust release build, `pow` benchmark at 2 MiB / 4,096 rounds on the dev
  machine, median of 30 runs.
- Target: C++ release build within **±20 %** of the Rust baseline at P3; faster is
  a bonus, not a requirement.
- If C++ is materially *slower* after P3, stop and investigate before P4. A slower
  miner changes the security story even though it does not change consensus.

No optimisation is allowed to change a hash. `-ffast-math` is banned in the kernel
target precisely because it can.

## 8. Language allocation

| Language | Used for | Explicitly not used for |
|---|---|---|
| **C++20** | kernel, policy, node, RPC, wallet, CLI, daemon, unit tests, benchmarks | GUI (kept in Rust), test orchestration |
| **Python 3.11+** | functional tests, test framework, vector capture, soak reporting, CI glue | anything in the shipped node |
| **C** | see below | — |
| **CMake ≥ 3.25** | build of the C++ tree, ctest integration | anything at runtime |
| **Shell** | `scripts/*.sh`, CI steps, packaging | business logic |

### When C is justified `[PROPOSED]`

The task allows C "only where justified". The default is **no C at all**, and at
the time of writing no component meets the bar. A component may be written in C
only if it satisfies all four:

1. it is a leaf with no allocation and no error handling beyond an integer return;
2. it is hot enough that a C++ compiler's code generation is measurably worse, or
   it must be shared with a C-only consumer;
3. it has a C++ header wrapper with `extern "C"` and no C types leaking into the
   kernel API;
4. its output is covered by the same golden vectors as the C++ path.

The only plausible candidate is the scratchpad inner loop (SIMD/intrinsics
portability). It stays C++ unless P3's benchmark shows a concrete gap and a C
translation closes it without changing a single hash.

## 9. Rollback

- P0–P4 touch no shipped artefact. Rollback is `git revert` of documentation and
  new C++ files; Rust is untouched by construction.
- P5 introduces a second binary. Rollback is "do not ship it"; the Rust binary
  remains the release.
- P6–P8 have no automatic rollback for a *released* C++ node — which is why G6 is
  a 14-day soak and G8 is a written decision, not a commit.
- Because the chain has no reorganisation path (F1), a consensus defect found after
  cutover cannot be repaired by rolling back a few blocks. This asymmetry is the
  main reason the gates are strict.

## 10. What "done" means for this milestone

This document plus `01`, `02`, `04`, and `05` constitute milestone 1. It is done
when:

- every statement about the Rust tree is labelled and traceable to the commit;
- the twelve risks in `04` have a mitigation and a trigger;
- the gates in §4 and the test layers in `05` are specific enough that a developer
  who has never seen this repository can start P0 on Monday.
